## Findings (PAN-034 frontend consult, read-only)

**Current state**
- `app-credential-issue-dialog.tsx`: confirm phase has no form. `onIssue` calls `issue.mutateAsync(setSecret)`. `useIssueCredentialMutation` (`src/features/apps/api/queries.ts`) POSTs with NO body, and an existing test asserts `await writes(seen,'POST')[0].text() === ''`. That test must change. The reveal and clear logic (ADR 0007) is self-contained and should not be touched. The mutation takes `onSecret` as its only variable, so the scope has to be added as a variable, e.g. `{ scope, onSecret }`.
- `credentialIssueError` handles 409 reasons `admin_app`, `app_disabled`, `credential_limit` (copy says "This app already has 2 active credentials"; must become per scope). It has no mapping for scope-specific refusals such as `limits:write` refused until ADM-044, or `admin` app with a non-`releases` scope. Those currently fall to the generic 409 text or `fallback` (server `message`). Add a 422/409 reason map. Check the real reason codes in org-admin-api (`apps` credential router) before coding. Do not guess them.
- `app-credentials-tab.tsx`: columns are Key ID / Status / Created / Last used / Actions, and `colSpan={5}` on the empty row (must become 6). Copy "An app can have at most 2 active credentials" appears in the tab and in the dialog description; both must become per-scope. The list is paged (`CREDENTIALS_PAGE_SIZE=20`), so "active per scope" computed from the visible page can be wrong when there are more than 20 rows. Revoked rows accumulate, so this is plausible over time.
- Edit dialog is `app-form-dialog.tsx` (shared register/edit). It already sends a changed-fields-only PATCH (`changed` object built with conditional spreads). `appFormSchema` has no role fields. `SelectDropdown` takes `{label,value}[]`, `isControlled`, `disabled`, `isPending`. Note it has no way to attach `aria-describedby`.
- `app-detail-sheet.tsx` `AppOverview`: `roleId()` renders the raw uuid in `<code>` for default and org owner (org owner only when `org_mode === 'required'`). There is no super-admin row.
- Role data: `allRoleDefinitionsQueryOptions(app, api)` in `src/features/roles/api/queries.ts` fetches ALL role definitions of an app (pages of 100, key `rolesKeys.allDefinitions(app)` nested under `appsKeys.detail(app)`). Each row has `id`, `key` (e.g. `simap:admin`), `name`, `is_default`. This is the "no N+1" source for both the selects and the sheet (one query, then `Map<id, RoleDefinition>`). It is nested under the app detail key, so `useUpdateAppMutation` (invalidates `['apps']`) refreshes it too.
- `src/api/schema.d.ts` / `openapi.json` snapshot: `AppRead`/`AppUpdate` have `default_role_id` and `org_owner_role_id` but NO `super_admin_role_id`; credential `scope` and the `AppCredentialScope` enum are absent (grep: no `super_admin` anywhere in src). The R2 types must be regenerated for just these fragments (as PAN-018 did); no hand types.
- Permission registry (`src/lib/permissions/registry.ts`): `apps.update` = `admin:apps:write`; `apps.issueCredential` = `admin:apps:write` (the `admin:*` requirement is only prose in the UI). `users.viewSessions` shows the existing pattern for `admin:*` actions: `perm('admin:*', ...)`. `Can` supports `disable` (render-prop `{disabled, describedBy}`; shows "Requires admin:*" text) for a single `ActionId`. `unknown` permission state renders enabled (API is the gate).
- Tests use `fakeApi(appsServer(write))` from `@/test-utils/api` plus `renderApps` in `test-fixtures.tsx`. `appsServer` serves GET `/apps/{key}`, `/permissions`, `/credentials`, `/join-requests` from fixtures, but NOT `/role-definitions`, so a role-definitions GET would currently 404. `writes(seen, 'PATCH')` / `.text()` inspects request bodies. `WithPermissions granted=[...]` controls permissions.

## Recommendations

1. **Types (AC all)**: refresh only the needed openapi fragments (`AppCredentialScope`, `AppCredentialRead.scope`, `AppCredentialIssue` body, `AppRead/AppUpdate.super_admin_role_id`). Export `AppCredentialScope` from `app-schema.ts` via `components['schemas']`. Add a compile-time `Same<>` guard against a zod enum, as the file already does for other enums.
2. **Scope select in the issue dialog (AC1, AC4)**:
   - Add a small `credentialScopeOptions(appKey)` helper in `data/data.ts`: `admin` returns `[releases]`; other apps return all except `limits:write`. Include a one-line hint per scope and a `runtime: true` flag for `org-members:read` and `usage:*`, which adds the "backend deploy environment only, never CI or browser code" text.
   - Use react-hook-form + a tiny zod schema `credentialIssueSchema = z.object({ scope: z.enum([...]) })` with `defaultValues` scope `''` or undefined and `'Select a scope.'` as the required message. Do not preselect `manifest`, to honour "required". For the `admin` app the dialog is unreachable today (the tab hides the Issue button), but keep the option helper correct and unit-tested anyway.
   - Keep the confirm-phase markup and aria-disabled pending pattern. Do not wrap the secret field in the form (a test asserts the reveal input is not inside a form). A `<form>` only around the select + submit is fine, and it is unmounted in the reveal phase.
   - Mutation vars `{ scope, onSecret }`; body `{ scope }`. Update the existing "no body" test to expect `{"scope":"manifest"}`.
   - Wire the double-click guard (`inFlight`) unchanged.
3. **Refusal mapping (AC3)**: extend `credentialIssueError` with per-scope `credential_limit` copy that names the scope ("already has 2 active `<scope>` credentials. Revoke one, then issue a new one."), plus the scope-refusal reasons (limits:write not available yet; admin app only `releases`; 422 `validation_error` on `scope`). Keep an unknown-reason default that is specific, not silent. Add a table-driven test in `errors.test.ts`, the same style as the existing tests.
4. **Tab (AC1)**: add a "Scope" column (`<code>` or Badge with the scope value; fall back to `manifest` for legacy rows only if the API can omit it, check the schema). Update `colSpan` to 6. Compute the active count per scope and show a per-scope summary line, e.g. "manifest 1/2, org-members:read 0/2". To avoid the 20-row paging error, either (a) fetch active counts from a separate unpaged-up-to-100 query, or (b) disable the dialog's scope option client-side only as a hint and always rely on the API `credential_limit` 409. Recommend (b) plus a hint computed from the visible page, labelled as such. Do not block the Issue button from limited data (R4/R1: the API owns the rule). Pass the active counts to the dialog only to annotate options ("2 of 2 active"), never to hard-disable them.
5. **Edit-app role fields (AC2, AC4)**:
   - Add to `appFormSchema` (edit-only use): `default_role_id`, `org_owner_role_id`, `super_admin_role_id` as `z.string()` with sentinel `'none'` (Radix Select forbids an empty-string item value). Map `'none'` to `null` on submit, and `null` to `'none'` in `defaultValues`. Create mode must not render or send these fields.
   - Render the three `SelectDropdown`s (label = `${key} — ${name}`) only when `isEdit`, fed by `useQuery(allRoleDefinitionsQueryOptions(app.key, api))`. Show `isPending` and a role-load error state; while loading or failed, disable the fields and keep the current value shown (do not blank them, or a save could clear them). Because a role id missing from the list (deleted) would render an empty select, add the unknown id as a fallback item.
   - Extend the existing `changed` diff: `...(values.default_role_id !== initial.default_role_id && { default_role_id: toApi(...) })`, comparing normalised values (`'none'` vs `null`). Reuse the "nothing changed, no request" branch. Unit-test the pure diff by extracting it to `data/` (e.g. `appUpdateDiff(currentRow, values)`), and test that an untouched role never appears in the PATCH.
   - Org owner role: show only when `org_mode` is `required` (matches the sheet) and note it must stay Required while set. Offer "None" for default and org owner; for super-admin offer "None" only if the API allows clearing (ticket says "where allowed"; verify in the OpenAPI/ADR-0030, and when it is not allowed, omit "None").
   - Super-admin: add `ACTIONS['apps.setSuperAdminRole'] = perm('admin:*', 'PATCH /api/v1/apps/{key}')` in the registry and use a permission hook (`useActionPermission`) or `<Can action=... disable>` to disable the select and show "Requires admin:*" linked by `aria-describedby`. `SelectDropdown` needs a small extension (pass `aria-describedby`/`id` through to `SelectTrigger`) or wrap with a description `FormDescription`. Also exclude the field from the diff when disabled. Note the API only enforces `admin:*` when the value changes, so sending an unchanged value is harmless, but the diff already omits it.
   - The "None" semantics on the admin app: the API 409s on a default role for `admin` (see `appFormError`), so hide or disable the default role field for the `admin` app, with a note.
6. **Refusals on PATCH (AC3)**: extend `UNPROCESSABLE_FIELD`/`appFormError` and `AppFormField` with the three role fields. Map the reasons already known in `roles/data/errors.ts` (`role_has_admin_permissions`, `role_has_org_permissions`, `unknown_role`, `same_as_default_role` (note the existing copy for this one speaks from the default-role side; for the owner-role field word it for the owner side), `org_mode_required`). Confirm the actual reason code for "owner == default" and for "admin-only permission held by the owner role" in org-admin-api, and add the 403 copy for super-admin without `admin:*` (the `isForbidden` fallback renders `ForbiddenPanel` already). Show each as an inline field error (`form.setError`) on the matching select, with the 409 `CHANGED` text as the fallback alert.
7. **Detail sheet (AC2)**: in `AppOverview`, load `allRoleDefinitionsQueryOptions(app.key, api)` once (enabled only while the sheet is open and when at least one role id is set), build an `id -> key` map, and render `<code>{key}</code>`. Fallback while loading: "Loading…" (not the raw uuid); on error or a missing id, show the id plus a note. Add the Super-admin role row (only when `super_admin_role_id` is present in the schema). Since the sheet and the edit dialog share the cached query key, there is no extra fetch. Make `useUpdateAppMutation` success refresh `appsKeys.all`; that already refreshes `appQueryOptions` (so the sheet shows `simap:admin` after save).
8. **Tests (AC4)**, all with `fakeApi` network fakes:
   - Extend `appsServer` with a `/role-definitions` branch (`ROLE_DEFINITIONS[app.key]`, a Page with `items`, `total`) and add `simap` + roles (`simap:admin`, `simap:member`) to `test-data.ts`.
   - Scope options: parametrised render of the dialog for `calechip` (5 options, no `limits:write`) vs `admin` (only `releases`) via the pure helper and via the DOM.
   - Request body: select `org-members:read`, submit, and assert the POST body is `{"scope":"org-members:read"}` (parse `await req.json()`); submit without selecting a scope shows the "Select a scope." error with no POST; double-click still produces one POST.
   - Tab: Scope column text; per-scope hint with a fixture of 2 active `manifest` + 1 `releases`.
   - Edit PATCH diff: change only the org owner role to `simap:admin`, assert the body is exactly `{"org_owner_role_id":"<uuid>"}`; "None" yields `null`; no change means no PATCH; admin without `admin:*` (via `WithPermissions granted`) disables the super-admin select and shows "Requires admin:*".
   - Sheet: after a PATCH, the refetch returns the new `org_owner_role_id` and the sheet shows `simap:admin`, never the uuid. Assert only one `/role-definitions` request.
   - Refusals: table-driven tests for `credentialIssueError` and `appFormError` plus at least one DOM test per surface (409 `credential_limit` per scope, a 422 owner==default error on the org owner field, 403 panel).

## Risks
- The openapi snapshot lacks the fields; if org-admin-api `main` names differ (e.g. enum values or `super_admin_role_id` nullability), the typecheck will not catch it until regenerated. Verify against `/openapi.json` first.
- Roles list truncation: `allRoleDefinitionsQueryOptions` throws after 50 pages; fine, but errors must be handled in the edit form so a failed role load never blanks or clears role values on save.
- Sending `null` for a role the user never touched would clear it (R9 data loss). The diff must compare against the original and omit untouched fields; add a test for it.
- `SelectDropdown` with an empty-string value is invalid in Radix; use a sentinel.
- Dialog is a shared create/edit form; role fields must be edit-only or create mode may send unexpected keys.
- Existing tests that assert an empty POST body or "most 2 active credentials" copy will break by design; update them in the same change.
- The 2-active limit per scope computed from a paged list can mislead; rely on the API's 409 as the source of truth.
- Credential-secret handling must remain identical (no secret in TanStack state, `gcTime: 0`, `retry: false`).
